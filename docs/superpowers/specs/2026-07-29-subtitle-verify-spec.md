# Spec：字幕校对（对齐检测 + 一键校正）

**日期**：2026-07-29（2026-07-30 修订：§4.2.1 对照时间轴升级为可交互 + §4.2.2 挂载分级）
**状态**：后端已实现（9 提交，2336 测试绿）；前端芯片已实现；对照时间轴待实现
**范围**：给已装字幕做时间轴对齐检测，检出偏移时提供一键校正。**不做播放器、不做样式渲染。**

**2026-07-30 修订摘要**（三条源自用户裁决 + 实测，均推翻了初稿的判断）：

1. **对照泳道升级为 PR 风格可交互时间轴**（块显文字 / hover 浮层 / 滚轮缩放 / organic 波形）。
   用户澄清了铁律边界：「不增添心智负担」是指别暴露我们多累，而这里**恰恰要用图形化证据说服
   用户**点校正按钮。不暴露机械 ≠ 不给证据。
2. **"云盘不可用"改为 fstype 三态分级**。实测发现生产库 492 个条目**全在 CIFS 上**，
   原规则会禁掉全部；真正跑不动的只有 fuse.rclone 那 27 个。
3. **两处自我更正**：包体积约束作废（实测 gzip 152 KB，局域网自托管场景不敏感）；
   peaks.js 的 LGPL-3.0 排除理由错误（该协议允许静态链接，闭源代码仍闭源），改按工程理由否。

## 1. 为什么做这个（不做播放器）

用户原始诉求："让用户能观察字幕找得对不对"，最初想的是接播放器。调研（`2026-07-29-playback-options.md`，792 行）证明播放器这条路不可行，三条独立致命障碍：

1. **DTS-HD MA / TrueHD 在任何浏览器都无法解码** —— 约一半库是 REMUX，需服务端转音轨，软路由转不动
2. **Chromium 故意不提供 HEVC 软解码器**（专利责任，官方 Intent-to-Ship 原话："we will not provide a software implementation to fall back to"）→ 播放是客户端机器的彩票，且**失败是静默的**
3. **MKV 在所有浏览器的 `<video>` 里都不支持**；jellyfin-web 至今有 2026 年的开放 bug（#7651）静默 0ms 失败

同类产品的信号更强：**Bazarr 做了约 8 年，没有播放器也没有预览**，社区对"怎么验证"的官方回答是"用你自己的播放器看"。Bazarr+ 真要解决时，做的是**时间轴前后对比 diff + 文本编辑器**。而 Sub-Zero（把自己嵌进媒体服务器的字幕工具）首页第一行是 "THIS PLUGIN IS DEPRECATED, PLEASE USE BAZARR"。

**关键认知（用户提出，实测确认）**：WebDAV/rclone 让云盘文件"元数据能读，内容读不了"——`stat` 秒回、ffprobe 读头部 10-16s 还行，但随机读内容每次 seek 都付阿里云 CDN ~12s 延迟地板。实测：云盘局部解码 20 秒音频要 **223 秒**。这个认知会反复影响以后的判断（缩略图、章节检测、指纹比对都会撞同一面墙）。

### 真正没被解决的问题

| 问题 | 现状 |
|---|---|
| 装错剧 | ✅ 已被 two-evidence bar + 结构检查拦住（446 文件零身份错误） |
| 装错集 | ✅ 已被季包 fileList 匹配拦住 |
| **时间轴偏移** | ❌ **完全没检查**。内容 100% 正确但整体偏 8 秒，全程对不上嘴 |

偏移的成因与"找错"无关，是**版本差异**：同一集 BluRay 版 vs WEB-DL 版片头长度不同就差几秒。字幕组按 A 版做，用户文件是 B 版——**没有任何前置关卡能拦住**。

## 2. 用户裁决（写死，实现不得偏离）

1. **只有绿和红，绝不给黄。** 用户不想看数字，只想看一片绿。给黄色会让用户觉得"这项目有病"，而我们本意是诚实——那就本末倒置了。
2. **置信度/偏移量/参考源层级只存内部**，供 trace/审计/调试；UI 不展示任何数字。
3. **是否校正是用户的选择。** 内嵌轨不准是**源的问题不是我们的问题**——我们只如实报告观测到的差异，不保证内嵌轨是真理。用户看画面一眼就知道该不该修。
4. **入口在剧集行内**，用状态芯片（不用眼睛图标——"拟人化的太吓人了"）。
5. **不做样式预览（JASSUB）**：用户在乎字幕对不对、有没有对齐，不在乎样式本身。
6. **不做播放器**；未来可选加"外部播放器 URL 模板"设置项（用户已有 Jellyfin/Emby/Plex 时深链跳转），零维护、不捆绑容器。

## 3. 技术方案（自研 TS，零外部依赖）

### 3.1 为什么不用 ffsubsync / alass

| | alass | ffsubsync | **自研 TS** |
|---|---|---|---|
| 架构覆盖 | ❌ **只有 x86-64**，无 ARM release（实测 GitHub API 确认），最后 release 2019-10-10 | ✅ numpy 有 aarch64 wheel | ✅ **天然全平台** |
| 镜像代价 | 2.9MB 静态 musl（但仅 amd64） | **+150~250MB**（Python+numpy+scipy） | **0** |
| `.ass` 安全 | byte-identical 除 Start/End，但**强制转 UTF-8、剥 BOM、CRLF→LF** | ❌ 经 pysubs2 round-trip **丢 section** | ✅ **我们自己写，非 Dialogue 行一个字节不碰** |
| 维护 | ❌ 停滞（2021 最后提交，36 open issues） | ✅ 活跃 | 自己的几十行 |

**用户裁决**：ARM 用户用不了是产品级硬约束（"很多用户想用，他们的硬件就不支持"）→ alass 出局。

### 3.2 算法（已 PoC 验证）

离散化 + 互相关，标准做法：

1. 把两边 cue 序列离散成 100ms 步长的"有人说话"布尔数组
2. 在 ±60 秒窗口内滑动，用 **Jaccard（交集/并集）** 打分——不能用"交集/min"，实测那样对一方 cue 密集时会虚高
3. 取最高分的位移 = 偏移量，该分数 = 可信度

**PoC 实测（700 cue / 43 分钟节目，66ms）**：

| 场景 | 检出偏移 | 分数 | 判读 |
|---|---|---|---|
| 整体晚 8.3s | **+8300ms** 精确 | **1.000** | 高分 → 可校正 |
| 完美对齐 | 0ms | **1.000** | 高分 → 绿色沉默 |
| 完全无关字幕 | 乱数 | **0.517** | 低分 → 不敢报，判"无法验证" |
| 帧率不匹配 23.976/25 | 乱数 | **0.526** | 低分 → **平移修不好，不给校正按钮** |

阈值：**≥0.9 可信 / <0.7 不可信**。第 4 个场景证明低分有价值——帧率漂移拿不到高分，所以不会错误地给一个平移修不了的病提供"一键校正"。

### 3.3 参考源三层降级（实测覆盖率）

| 层 | 参考源 | 覆盖 | 成本 |
|---|---|---|---|
| ① | 内嵌字幕轨（任意语言——只看说话时段，不看内容） | **63.7%**（已探测 394 项中 380 项有轨，全 `subrip` 文本格式） | **亚秒级**，提取近乎瞬时 |
| ② | 同目录其他字幕（如简繁两份、旁边的 `.eng.srt`） | 覆盖部分 ①未命中项（莉可丽丝那批就有简繁双份） | **亚秒级** |
| ③ | 音频 VAD（仅本地文件） | 剩余本地文件 | 本地整轨解码 **14s**（实测 speed 111x） |
| — | **云盘且无①②** | 不做 | 云盘解码不可行（223s/20s），界面如实说明 |

**③ 后置甚至可能不做**：①②已覆盖大部分；若做，需 ffmpeg 解码（镜像已有）+ 自研 VAD。

### 3.4 写文件（最高风险处）

**只改 `Dialogue:` 行的 Start/End，其余字节原样保留**——`[Fonts]`/`[Graphics]`/`[Aegisub Project Garbage]`/字幕组注释/原始编码/BOM/CRLF 全不动。这比 alass 的"byte-identical 除 Start/End"更彻底。

安全依据（调研确认）：ASS 的 `\move`/`\pos`/`\t`/`\fad`/`\k` 等内联标签时间**相对于行首**，故只改 Start/End 不破坏它们。

必须做到：
- **原子写**：写临时文件 + rename（CIFS/rclone 的 rename 语义调研未完成 → 实施时必须实测）
- **备份原文件**，支持撤销
- **幂等**：防止连点两次导致双倍平移（DB 记录已应用的校正 + 内容哈希）
- **失败不留半成品**

## 4. 界面（视觉伴侣已确认）

### 4.1 入口：剧集行内的状态芯片

复用现有 `EpisodeRow.tsx` 设计语言（5px 语义点 + mono 集号 + 剧照 + 日期）。**只有两种状态**：

- **绿**：无问题（或无法验证——见 §4.3）→ 无动作，安静
- **红**：检出可校正的偏移 → 可点击

### 4.2 检视面板（点红芯片打开）

三块，对齐校正是主角：

1. **结论条**（顶部最显眼）：一句人话 + 成因猜测 + 两个按钮「校正时间轴 / 保留原样」
2. **对照时间轴**（2026-07-30 升级，用户裁决）：见 §4.2.1
3. **台词列表**：时间戳 + 台词，可滚动。装错剧时扫一眼就能发现

#### 4.2.1 对照时间轴（可交互，PR 风格）

**用户裁决的定位**（2026-07-30，重要——它划清了与铁律③的边界）：

> 「不要增添心智负担」是指**没必要时不该向用户暴露内部工程语、不该说我们做得多累**。
> 但**这里是我们要用图形化证据说服用户**：字幕偏了、怎么偏的、我们有一键对齐。
> 正因为要说服他们，才需要泳道，甚至更专业的图形。

即：**不暴露机械 ≠ 不给证据**。前者是别让用户操心我们多累，后者是让他看懂"为什么这个按钮值得点"。
泳道属于后者，因此**不受"零数字"铁律约束的是图形本身**——但仍然不写分数/偏移量数字。

**必须支持的交互**（用户明确要求）：

| # | 交互 | 说明 |
|---|---|---|
| I1 | 块上直接显示字幕文字 | 块够宽显示，窄了 `text-overflow: ellipsis` |
| I2 | hover 弹浮层显示完整文字 | 含该块精确起止时刻 |
| I3 | **滚轮缩放时间单位** | 以光标为锚点，不是缩到中心（那样会跟丢正在看的位置） |
| I4 | 横向平移 | 拖拽 |
| I5 | **两轨严格同步** | 缩放/平移联动，否则对照失去意义 |

**第三轨：音频波形**（仅局域网/本地，见 §4.2.2）。

**技术选型**（调研 `2026-07-30-timeline-libs` + `2026-07-30-waveform`）：

- **主视图自绘 DOM + d3-scale/d3-zoom**（12.4 KB gzip，ISC）。
  - 为什么不用现成时间轴库：需求里最难的 **I5（双轨严格对齐）在自写方案里是免费副产品**
    （两轨读同一个 `{startTime, pxPerSec}`），而在每个第三方库里都是"要么内建、要么根本做不到"
    的二元选择。难点恰好落在库帮不上忙的地方。
  - 用 DOM 而非 Canvas：文字省略号、hover、焦点、无障碍全部由浏览器免费提供。
  - 「字幕专用时间轴组件」这个生态位实测是**空的**（查了 6 个：SubPlayer 949★ 自称停维护、
    react-subtitle-editor 仅 15★ 且把 react 写进 dependencies 会致 React 双实例、
    SnakeLil/subtitle-editor **无 license 文件**=不可商用、另三个停在 2016~2018）。
- **波形用 wavesurfer.js v7**（12.2 KB gzip，BSD-3，零依赖）+ 自定义 `renderFunction`
  画 d3-shape `curveCatmullRom` 镜像包络（tree-shake 后 2,805 B）。
  - 关键验证（查 dist 源码非文档）：`setOptions({peaks, duration})` 走**纯峰值路径**，
    `blob.arrayBuffer()` 解码是 `else if` 分支会被完全跳过 —— 正合"后端 ffmpeg 抽峰值喂前端"。
  - 审美要求 **organic**：上下镜像对称 + 平滑曲线包络 + 垂直渐变（SoundCloud / iOS 语音备忘录
    质感），**不是**等宽硬边竖条（用户原话「糙了点」）。
- **peaks.js 已否，但理由不是 license**：LGPL-3.0 §4(d)(0) 明确允许静态链接，且
  Minimal Corresponding Source 定义排除"基于本应用"的部分——闭源代码仍闭源，
  "LGPL 逼你开源整个应用"是误解，真实合规成本约一天一次性。
  **按工程理由否**：4.38 MB + 依赖 Konva，且其审美是刻意分析型的，与 organic 相反。
- **体积约束已作废**：实测当前 bundle gzip **152 KB**，这是局域网自托管 dashboard，
  不是公网首屏。此前"体积敏感"的判断未核实部署场景，是错的。

#### 4.2.2 云盘：禁用对照图，但不禁用检测

**实测数据（2026-07-30，在生产容器内跑的）**：

| 挂载点 | fstype | 视频数 | 抽整轨波形 |
|---|---|---|---|
| `/media/tv` | **cifs** | 436 | **8 秒** ✓ |
| `/media/anime` | **cifs** | 46 | **8 秒** ✓ |
| `/media/movies` | **cifs** | 10 | **8 秒** ✓ |
| `/media/aliyun` | **fuse.rclone** | 27 | **>120 秒** ✗ |

**关键发现**：生产库的三个主要媒体目录**全是 CIFS（网络挂载）**，共 492 个条目。
所以「是网络挂载就禁用」这条规则会**禁掉全部 492 个**，而真正跑不动的只有云盘那 27 个。

**真正的分界不是"网络 vs 本地"，是"局域网 vs 公网云盘"**：局域网走千兆内网、seek 毫秒级；
公网对象存储每次 seek 付 ~12 秒 CDN 延迟地板。两者都叫"网络挂载"，性能差三个数量级。

**判据：fstype 白名单**

| fstype | 判定 | 理由 |
|---|---|---|
| `ext4` `btrfs` `xfs` `zfs` `overlay` | 可用 | 真本地 |
| `cifs` `smb3` `nfs` `nfs4` | **可用** | 局域网协议，实测 8 秒抽完整轨 |
| `fuse.rclone` `fuse.davfs` `fuse.sshfs`(公网) | **禁用** | 公网对象存储，seek 付 CDN 延迟地板 |
| `fuse`（无子类型） | **禁用** | 判不出来 → 保守当云盘 |

**检测手段**（已在生产容器验证）：读 `/proc/self/mountinfo`，最长**路径段**前缀匹配
（`realpath()` 归一后），over-mount 时后者胜。

- 容器内**能看到原始 fstype**：bind mount 共享 superblock，上表就是从生产容器读出来的。
  此前担心的"容器内看不到宿主 fstype"不成立。
- **必须用 `mountinfo` 而非 `/proc/mounts`**：前者带 **FUSE 子类型**
  （`fuse.rclone` vs `fuse.mergerfs`），而 `statfs` 的 magic number 把所有 FUSE 压成同一个值。
- 约 80–120 行，零依赖，无原生模块（ARM 天然可用——magic number 是架构无关的内核常量）。
- **判不出来默认禁用**：误判成云盘只是灰掉一个按钮；误判成本地会让 ffmpeg 从 WebDAV
  拉几 GB、挂死 worker。方向不对称，往安全侧倒。
  注：现有硬编码 `media_roots.type='local'` 恰恰错在危险方向。
- 已知失败模式：宿主在容器启动**后**才挂载 rclone 时，默认 `rprivate` 传播会让容器看到
  底层空 ext4 → 误判为本地。缓解：`bind-propagation=rslave`，或依赖"判不出来即禁用"。

**云盘条目的界面行为**：

- 芯片**仍然亮红**（检测在云盘上照样能做——它只读字幕文件，不解码音频）
- 红芯片**点不开对照图**，hover 提示说明原因，并给出**仍然可做的事**：盲校正
  （偏移量后端已算出）
- 文案定位（用户裁决）：云盘的价值是「字幕能下进去」，这已实现；对照图做不了是
  **网盘的物理限制，不是功能没做**。文案必须传达这个区别，不能让用户以为我们偷懒。
- **不显示空的声音轨**（而非显示一条永远加载不出来的）——前两条字幕轨已足够回答"能不能修"

### 4.3 诚实但不制造焦虑

- 对齐良好 → **沉默**（不显示"aligned 0.94"——那是兑现不了的承诺）
- 无法验证（无①②）→ **也当绿色**，不给黄。诚实体现在**不假装验证过**，而非打黄标让用户焦虑
- 参考源层级/分数/偏移量 → 只进 trace 和 DB
- **例外（2026-07-30 澄清）**：§4.2.1 的对照时间轴是**图形化证据**，它的存在正是为了说服用户
  点校正按钮。它不显示数字，但显示形状——这与"零数字"不冲突，因为不要求用户做计算或判精度。

## 5. 不做什么（YAGNI）

- **播放器**（§1 三条障碍）
- **JASSUB 样式预览**（用户裁决：不在乎样式本身。四块里价值最低、风险最高：WASM + canvas + React 生命周期 + CJK 字体陷阱）
- **公网云盘的音频波形与对照图**（实测 >120s 抽 60s 音频；见 §4.2.2。
  注意：**局域网 CIFS/NFS 不在此列**，实测 8 秒抽整轨，照常提供）
- **云盘视频截图**（26s；本地 2.9s 可缓存，但一致性差 → 第一期不做）
- **捆绑 Jellyfin 容器**（用户 13 天前的去 Jellyfin 化裁决仍然正确，调研佐证）
- **拉伸校正（帧率修复）**：第一期只做平移。帧率不匹配检出后如实告知"平移修不了"，不提供按钮
- **时间轴上的编辑操作**（拖块改时间、resize、吸附）：对照图是**只读证据**，不是字幕编辑器。
  唯一的写动作是结论条那个「校正时间轴」按钮。这条排除砍掉了自写时间轴的大部分复杂度
  （工作量因此是 9–14 小时而非数倍）

## 6. 验收标准

1. PoC 的四个场景在真实字幕文件上复现（偏移/对齐/无关/帧率）
2. 63.7% 有内嵌轨的条目**亚秒级**出结果
3. `.ass` 校正后：非 `Dialogue:` 行**逐字节不变**（含编码、BOM、CRLF），`diff` 只显示时间戳行
4. 连点两次校正 → 只平移一次（幂等）
5. 校正可撤销，原文件可恢复
6. UI **零数字**（grep 断言界面不出现分数/偏移量）。
   **例外**：对照时间轴的刻度尺可以有时刻标签（`12:10`）、hover 浮层可以有该块起止时刻——
   那是**定位坐标**不是**质量评分**，见 §4.3 最后一条
7. 无参考源的条目显示绿色，不显示黄色/警告
8. 全量测试绿 + tsc 0 errors

**对照时间轴专项（2026-07-30 新增）**：

9. **I5 回归锁**：缩放到任意级别后，两轨上同一时刻的像素 x 坐标必须相等
   （断言两轨读同一 viewport state，不是各算一份）
10. **滚轮以光标为锚点**：在时间轴某点滚轮缩放后，该点对应的时刻必须仍在光标下
    （不是缩到视口中心）
11. **块文字**：块宽 > 阈值时渲染字幕文本；hover 出浮层含完整文本
12. **挂载判定**：给定 `/proc/self/mountinfo` 内容 + 路径，返回正确的 `local|lan|cloud` 三态；
    `fuse` 无子类型 → `cloud`（保守）；判不出来 → `cloud`
13. **云盘禁用态**：`fuse.rclone` 路径的红芯片可见但对照图入口 disabled，
    且**不渲染声音轨的容器**（不是渲染一个空的）
14. **局域网不被误禁**：`cifs` / `nfs` 路径必须**能**打开对照图 + 显示波形
    （这条是防止 §4.2.2 那个"禁掉全部 492 个"的回归）
15. **organic 波形**：渲染出的是镜像对称包络（上下两半关于中线对称），不是单向柱状

## 7. 风险

| 风险 | 缓解 |
|---|---|
| 内嵌轨自身不准 → 误报偏移 | 用户裁决：源的问题不是我们的问题。如实报告观测差异，校正是用户选择。文档说明清楚 |
| CIFS/rclone 的 rename 非原子 | ✅ **已实测（2026-07-30）**：CIFS（`//192.168.100.241/share`）与 rclone WebDAV（阿里云盘）双双支持 rename-over-existing，内容正确、无残留。方案可用 |
| 双倍平移 | DB 记录 + 内容哈希幂等门；测试锁 |
| 云盘写入延迟致校正"看起来没生效" | 已知云盘最终一致性（写探针 bug 就是它）→ 写后不立即验证，UI 说明可能延迟 |
| 帧率漂移被当成偏移 | 低分（实测 0.526）拦住；不给校正按钮 |
