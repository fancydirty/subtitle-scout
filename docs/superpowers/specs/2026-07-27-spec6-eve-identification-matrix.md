# Spec 6：B 线 —— eve 识别能力矩阵（最小必要条件实验）

**日期**：2026-07-27
**状态**：待用户批准
**范围**：用独立实验台测出 agent 识别能力的**边界**——缺哪些证据就必然认不出。产出反哺 Spec 2 的 `insufficient-evidence` 判据。
**索引**：见 `docs/superpowers/specs/2026-07-27-INDEX.md`

## 1. 为什么需要它（我此前的 eval 测不出什么）

我做的 `identityEval.live.test.ts` 已连续两轮 16/16 全绿（弱模型 mimo-v2.5，含 2012/1917/300/π/M/Oldboy 等推理 case）。但它证明的是**"有信号时 agent 能挖出来"**，**没有**证明：

1. **缺什么信号就必然挖不出来**（分界线在哪）
2. **"证据不足"这个判断本身准不准**（Spec 2 依赖它，误判会把可自愈文件永久钉死）

原因是我的 eval 每个 case 是**固定的一整份证据**（目录名 + 文件名 + 时长 + 内嵌语言），全给或不给。而要找分界线需要**逐维度削减**同一个资源的证据，看它在哪一档崩掉。这是矩阵实验，不是一 case 一断言。

用户的洞察（我认为是本 spec 的真正价值）：**系统提示不说"找字幕"，只说"代替机械刮削"**。我的 eval 里 agent 知道自己在为找字幕做准备，可能因此更倾向"给个答案好继续干活"。纯识别任务下它的**诚实度**（敢不敢说"我认不出"）可能完全不同——而 Spec 2 恰恰依赖这个诚实度。

## 2. 为什么用 eve 而不是扩展现有 eval

| | 扩展 `identityEval.live.test.ts` | eve 实验台 |
|---|---|---|
| 系统提示 | 绑死在 findSubtitleWorker 的"找字幕"人格上 | 可自由设成"代替机械刮削" |
| 证据削减 | 要改 worker 的 prompt 组装逻辑（污染生产代码） | 实验台自己控制输入 |
| 矩阵规模 | vitest 一 case 一断言，矩阵会爆炸成几百个 test | 实验台可以循环跑矩阵、输出表格 |
| 污染风险 | 高——为实验改生产 prompt 是我犯过的错 | 零，独立目录 |

用户已确认 eve 的现实性：开源（Apache-2.0）、`npx eve@latest init`、dev server 直接跑，**不需要 OrbStack 容器**。我此前担心的 preview 稳定性对一次性实验台不重要。

**关键事实**：eve 的 npm 包内**自带完整文档**（`node_modules/eve/docs`），README 明写 "so coding agents can read it locally"。实施时**必须先读本地文档再写代码**，不要凭网上博客的二手 API（已发现网上文章的 `defineSkill`/`skills: [...]` 写法与官方 `agent/skills/*.md` + `agent/tools/*.ts` 的文件系统约定不一致）。

## 3. 核心约束：必须复用本体 skill（用户裁决）

> 当然要复用，或者说从本体skill中拆出一份，让它只做识别，不考虑后面的找字幕，也就是子集的感觉

**这个要求已经天然满足了**——上一轮按 progressive disclosure 重构时，识别教法已经拆成独立文档 `src/agent/skills/identifyMediaSkill.ts`（意外收益）。它：

- 只讲识别，完全不涉及字幕搜索
- 是自包含的（`makeIdentifyMediaSkill()` 无参数，识别与语言/档位无关）
- 已有 10 条语义锚点测试（`identifyMediaSkill.test.ts`）

**做法**：实验台的 `agent/skills/identify-media.md` 内容**从 `identifyMediaSkill.ts` 生成**，不手抄。

- 手抄会漂移，漂移了实验结论就不适用于产品（这是我上一轮报告里就点明的硬要求）
- 加一个生成脚本 + 一致性检查：若两边不一致则实验台拒绝启动
- 工具语义也必须一致：`search_tmdb` / `get_tmdb_details` 的输入输出形状照 `src/agent/tmdbTools.ts` 复刻

## 4. 实验设计

### 4.1 系统提示（刻意不提字幕）

`agent/instructions.md` 的人格：**"你是媒体识别器，取代机械刮削器。给你一个文件的观测事实，你判断它是哪部作品。"**

必须明确允许"认不出"是合法输出——否则测不出诚实度。且不提任何下游用途（不提字幕、不提库）。

### 4.2 证据维度（可独立开关）

| 维度 | 内容 | 现实中会缺失吗 |
|---|---|---|
| D1 文件名 | 资源文件名原文 | 几乎不会（但可能是纯技术 token） |
| D2 目录名 | 父目录（必要时含祖父目录） | 会（文件直接躺在根下） |
| D3 时长 | ffprobe `duration`（秒） | 会（探针失败/未探测） |
| D4 内嵌字幕语言 | ffprobe 语言 tag 列表 | 常缺 |
| D5 结构提示 | 机械解析的 season/episode/absoluteEpisode | 会（无 SxxEyy 结构） |
| D6 `[tmdbid-N]` 标签 | 路径里的 id 标签（Spec 4） | 绝大多数缺 |

### 4.3 资源分类（用户要求的分情况）

| 类别 | 例子 | 说明 |
|---|---|---|
| C1 规范命名 | `Stranger Things S04E09 1080p.mkv` | 对照组，应 100% 认出 |
| C2 版权规避乱写 | `招z魂z4` | 真实库原型 |
| C3 乱码 | `H）后丨室（2026）` | 真实库原型 |
| C4 文件名无意义但目录有意义 | `2026.2160p.iT.WEB-DL...mkv` 在 `H）后丨室（2026）...` 下 | **用户特别点名的情形** |
| C5 fansub 标签 | `[诸神字幕组][莉可丽丝][01]` | 真实库原型 |
| C6 中文截断 | `铁.` | 真实库原型 |
| C7 纯数字/符号标题 | `2012`、`1917`、`300`、`π`、`M` | 需时长交叉印证 |
| C8 同名陷阱 | The Rig（2010 影 vs 2023 剧）、Peacemaker（芬兰 vs DC）、Oldboy（2003 vs 2013） | 需年份/kind 区分 |
| C9 **真正无意义**（关键） | `1.mp4` 在 `/movies/random/` 下 | **应该认不出**。测诚实度，不是测能力 |
| C10 vague 命名特例 | 子代理调研产出 | 见 §5 |

### 4.4 矩阵：控制变量法

对每个资源，跑一组**逐步削减**的证据组合。例：

| 档 | 给的维度 | 期望 |
|---|---|---|
| 全给 | D1+D2+D3+D4+D5 | 认出 |
| 去时长 | D1+D2+D4+D5 | ? |
| 去目录名 | D1+D3+D4+D5 | C4 类应崩 |
| 只给文件名 | D1 | 多数崩 |
| 只给目录名 | D2 | ? |
| 只给文件名+时长 | D1+D3 | C7 类应能过（时长锚定） |

**产出不是"通过率"，而是每个资源类别的最小必要维度集合。**

### 4.5 判据（三类，必须分开统计）

1. **识别正确**：tmdbId 与 ground truth 一致
2. **诚实认不出**：证据确实不足时，明确说"认不出"（**这是成功，不是失败**）
3. **幻觉**：证据不足却给出一个身份（**最严重的失败**）

第 3 类是真正要压到零的东西。C9 类的价值全在这里：若模型对 `1.mp4` 编出一个身份，说明 Spec 2 的 `insufficient-evidence` 分类不可信，那条设计要重做。

### 4.6 反哺 Spec 2

实验直接产出 Spec 2 需要的两样东西：

- **`insufficient-evidence` 的客观判据**：哪些维度组合下识别必然失败 → 写进 skill 作为判定标准
- **分类准确率基线**：模型能否正确区分"证据不足"与"识别失败" → 若准确率低，Spec 2 §6 的回退方案（全部按 `identification-failed` 处理）生效

## 5. 子代理调研任务：vague 命名特例

**并行于实验台搭建**，产出 C10 的素材。

调研范围：真实世界中会击败任何机械刮削器的病态命名——PT/BT 站的发布惯例、网盘分享的重命名习惯、Emby/Jellyfin 社区报告的刮削失败案例、纯数字/单字母/符号标题、同名不同作品、跨语言标题、年份缺失或错误、多作品混装目录、季度合集、剧场版与本篇同名等。

**执行纪律（用户明确要求，针对 API 断线）**：

> 如果是调研任务……它死了的话就确实完蛋……也许最佳实践是，调研任务让子代理边查边写入文件

所以：**子代理必须边查边增量写入文件**（`docs/superpowers/research/2026-07-27-vague-naming-cases.md`），而不是攒到最后一次性返回。断线时我能从残留文件判断已完成的部分，决定"信息够了"还是"接续派"。这条纪律写进索引文档，作为此后所有调研任务的通用要求。

## 6. 不做什么（YAGNI）

- **不部署到 Vercel**。本地 dev server 足够，实验是一次性的
- **不把 eve 引入主项目依赖**。独立目录，独立 `package.json`
- **不用 eve 重写生产 agent**。主项目跑自己的本地 tool loop，本 spec 不动它
- **不测字幕搜索**。实验台只有 TMDB 工具，没有字幕 provider
- **不追求矩阵全覆盖**（10 类 × 6 维度全组合 = 640 次调用）。先跑关键档位，按发现追加
- **不手抄 skill 文本**（§3）

## 7. 验收标准

1. 实验台能跑起来，模型为 mimo-v2.5（与生产一致，用户钦定）
2. `agent/skills/identify-media.md` 由 `identifyMediaSkill.ts` **生成**，且有一致性检查（不一致则拒绝启动）
3. 系统提示中**不含**任何字幕/库相关字样（grep 断言）
4. 矩阵可复现：给定资源 + 维度组合 → 可重跑
5. 产出一份报告：每类资源的**最小必要证据维度集合**
6. **C9（`1.mp4`）类的幻觉率为 0**——这是硬门，不是"越低越好"
7. 结论写回 Spec 2 的判据章节

## 8. 风险

| 风险 | 缓解 |
|---|---|
| 实验台 agent 与生产 agent 行为漂移 → 结论不适用 | skill 生成 + 一致性检查；工具语义照 `tmdbTools.ts` 复刻；**同一模型** |
| eve 是 beta，API 可能变 | 读包内自带文档（`node_modules/eve/docs`）而非网上二手信息；锁版本 |
| 单次调用的随机性被当成结论 | 每个格子跑多次（次数由实施定），报告给出**分布**而非单次结果。已有先例：R7/R8 两轮全绿才敢认 |
| 矩阵太大烧太多 token | 先跑关键档位；mimo-v2.5 便宜且用户明示不担心成本 |
| TMDB 配额 | 实验台可缓存 TMDB 响应（同一 ground truth 反复查同一 id）；`.archive` 式落盘缓存 |
| 调研子代理中途断线 | 边查边写文件（§5），断线可判断进度并接续 |
