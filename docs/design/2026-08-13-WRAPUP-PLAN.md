## 零、给每个 subagent 的通用底座（**必须贴进每次 prompt**）

### 验收：只用一条命令

```bash
npm run verify
```

四条判据缺一即失败：① 退出码 0 ② `numFailedTests === 0`
③ **每个 `testResults[].status === 'passed'`** ④ 文件数 >= 基线。

⚠️ **不许再手敲 `numFailedTests` 那套口径**——它对**空 describe** 完全免疫。
2026-08-13 栽过一次：commit message 写「146 文件 / 3272 用例 / 0 失败」字面为真，
而 vitest **退出码是 1**（两个 `describe` 被删空只剩壳）。`scripts/verify.mjs` 就是为此建的。

**当前基线**：后端 146 文件 / 3284 用例；前端 84 文件 / 975 用例。

### 本仓两个招牌病

| 病 | 形态 | 已栽 |
|---|---|---|
| **A** | 加了能力却没定**谁写 / 谁读 / 谁触发** | 12 次 |
| **B** | 把**中间量**说成**结论量** | 6 次 |

### ⚠️ 变异验证的十个陷阱（都真踩过）

1. 模块级 `throw` → vitest 报 `total=0`（**整个文件没跑**，不是"没变红"）
2. 探针插进块注释里 → 0 命中
3. `?.` 注入成了 no-op
4. 变异有类型错误 → `tsc≠0`，那时的红**全是连带**
5. 变异被自己的**注释字符串**匹配到 → 假阳性
6. `noUnusedLocals` 让删除型变异报 TS6133 → 同 4
7. anchor 不匹配 → 变异**根本没注入**
8. 空 `describe` → `numFailedTests` 看不见（见上）
9. **守卫自己是假的**：`as` 断言 / `Object.fromEntries` 会压掉类型检查；
   `_Missing[] = []` 对任何数组类型都成立
10. **"生产 0 行"不能证明死活**——本仓活表 `item_files` 同样 0 行，只有**静态可达性**能证明

**铁律：变异后先 `grep` 确认它落在可执行代码行 + 确认 `tsc=0`，才采信红数。**

### TDD 纪律（本轮新增）

先写**会红**的测试，再实现。提交前必须能回答：
「我这条测试，在实现回退到旧行为时会不会红？」——**用变异证明，不用嘴说。**

## 一、Task 清单

### T1 · 孤儿族整族裁决 ✅ 用户裁定「封存」（2026-08-14）

**用户原话**（被问及"手动重派"与"字幕时间轴自动巡检"两个能力还要不要）：
> 「a，先不管。b. 也不管。这俩都是目前先 archive 的功能。
>   不删但也不接，等现在有的功能测试没毛病了再说。」

**裁决落地**：
- **不删、不接线**，维持零 import 现状；三个 orphan 守卫继续钉住"仍是孤儿"这个事实。
- **删掉两处「一个发布周期」时限判据**（`handleWorkerTask.ts` / `subtitleVerifyRepo.ts`）。
  理由：本仓自 v0.1.0（2026-07-09）后再无 release tag，"一个发布周期"无可查定义
  → 判据永远停在"技术上还没到期"，是个**永不触发的自毁开关**，比没有判据更糟——
  它让人误以为这里有个会自己了结的机制。改成**人的裁决**：解封条件是
  「字幕获取主链路经 live test 确认无毛病后，由用户重新裁决接通还是删除」。

**取证推翻的两条假事实**（都被广泛引用过）：
1. ❌「删整族会让 `subtitleVerify` 的 246 条算法用例跑不了（靠 `addReplicaSubtitle` 当 fixture）」
   → **假**。`addReplicaSubtitle` 定义在**族外**（`libraryRepo.ts:1019`），删族带不走它；
   246 条里 213 条（alignDetect/referenceSource/shiftTiming/subtitleSpans/verifySubtitle）
   与本族**零耦合**，真实代价只有 verifySweep 的 33 条，其中仅 1 条涉及那个函数。
2. ❌「`item_files` 是活表恰好 0 行，可作为『行数不能证明死活』的例证」
   → **假**。它的唯一写入方 `ingest.ts` 已被物理删除，是**真的没有写入方了**。
   拿死表论证"0 行不代表死"，论据是空的。已换成经实测的 `series` 表
   （生产 0 行，但写入方 `upsertSeries` 注入 throw → 红 514 条/14 文件，是活代码）。

**取证的其它实测结论**：
- `handleWorkerTask` 比裁决说的**更死**：注入 throw **零红**——它的守卫只断言
  `typeof === 'function'` 从不调用。守卫比作者以为的弱一档。
- 族必须**整族进退**：我实测真删 `workUnit` + `subtitlePropagation` → tsc 报
  `TS2307 Cannot find module '../v2/workUnit.js'`（同族 `unidentifiedFindSubtitle` 编译期依赖它）。
  注入 throw 证不出编译期依赖，这是探针法的盲区。
- 三张表删族后的归属：`jobs` 有写有读**永远无消费方**（12 行陈旧记录一直堆着）；
  `parked_paths` 变无写入方死表（5 行冻结）；`item_files` 本来就已经是死表。
- 无外部调度：`docker-compose` / Dockerfile / shell 脚本里零处直接调族内文件。

### T5 · 季集解析器 ✅ 已完成并生产验证

**计划里的「63 个」是错的**——实测分成性质完全不同的两类：
- **51 个在 `staging-<uuid>/` 里**：不是解析器的错，是文件还没整理入库。**不属 T5**。
- **12 个在 `Season 01/` 里**：真·解析器缺陷（日文 `第05話` 不认）。

**对抗审计又推翻了「12 个」**：生产实际 **13 个**，第 13 个（ep04）比其余 12 个严重得多——
CRC 校验和 `(4FE33E90)` 里的 `E90` 被 R5 吃掉，DB 里是 `S1E90 / parse_confidence='high'`。
其余 12 个是**诚实的沉默**（`none`），ep04 是**自信的谎话**。第一轮实施完全没发现它。

**三个 commit**：
1. `cf0453c` 字符类补「話」+ CRC 排除 + 四处同义字符类收敛成共享常量 `CJK_EPISODE_MARKER_CLASS`
2. `1936d6c` 补变异暴露的三个零覆盖点
3. `a632836` **C48 解析器版本化重解析**——招牌病 A 第 13 次的结构性治法

**为什么需要第 3 个 commit**：审计发现前两个对生产**一行都改不了**。
`daemonV2.ts` 靠 mtime+size 指纹跳过，文件躺在 NAS 上不动指纹永不变，
全仓又无任何 reparse 通路 → 解析器改进永远不作用于存量行。
治法：`PARSER_VERSION` 常量 + `files.parser_version` 列，版本落后即使指纹未变也重解析，
但**只重算解析产物**（work_dir/season/episode/parse_confidence），
绝不碰运行状态（sub_status/attempt/…）。迁移**刻意不给 DEFAULT**——
写 `DEFAULT 1` 会让存量行当场被标成"已最新"，等于本失效模式换个马甲再来一次。

**生产实测**（v39 部署后）：`重解析 649 行` → 13 个日文文件全部 S1E1–S1E13 / high /
**ep04 从 S1E90 变成 S1E4**；全库 234 个 `covered` 一个没被冲掉。

**遗留**：`PARSER_VERSION` 递增仍依赖人的自觉（改了解析器忘记 +1 就不会重算，且无测试会红）。
候选治法是给规则表算内容哈希当版本，代价是改注释也触发全库重算。**待裁决。**
