## 零、为什么先不删旧前端

现有 `web/` 是 2.5 万行 / 210 文件 / 9 个功能区。实测清点后：**真正坏的只有约 4000 行**
（library 读旧表显示假数据、redispatch 假按钮、activity 的秒表空转），
其余 2 万行（settings / setup / auth / components / i18n）是**能用的资产**，
且 live test 全程都在用它们（改配置、看部署状态、apiKey 鉴权）。

先删 = 把还能用的 2 万行一起扔掉 + 失去改配置的界面 + 讨论新设计时没有参照物。
**顺序：先讨论清楚 → 边做边替换 → 全替换完再删旧代码。**

## 二、三个页面

### 2.1 活动页 —— 像 Steam 下载页

- 两个 tab：**字幕** / **翻译**
- 每个 tab 内分两段：**正在跑** / **已排队**
- **粒度 = 作品，不是集**（R-F4）。后端工作台本来就按作品取件，
  正在跑的那个可以显示"第 3/8 集"，队列里只显示"作品 + 这轮几集"
- **识别不进活动页**（R-F1）：它虽然用 agent 但耗时很短，不值得占一个 tab

### 2.2 通知页 —— 完成的成果

- 「XX 剧找到了 S01 的第 3/5/7 集」；电影就是「已找到字幕」
- **保留一周**（R-F3）。倒序流水，**不做已读状态**（少一个状态少一堆 bug）

### 2.3 媒体库页 —— 应有集 vs 实有集 vs 字幕情况

- 小卡片网格：**实线 = 实有集**，**虚线 = 应有但磁盘上没有**
- 右上角小圆点表示字幕状态：
  - 无点 = 没有中文字幕
  - **蓝点** = 内嵌中文轨（不需要处理）
  - **绿点** = 本项目配上的
- **不管来源，按充分必要条件算**（R-F2，防猴子用户）：
  两个「绝命毒师」目录，只要有**一处** S01E03 有字幕，媒体库就显示这一集已获取
  —— 即使另一处那份仍要单独去配。合并键 = `work_id`（TMDB id）
- **识别失败的孤儿不露出**：那是用户的命名问题，底线是按 `title (year)` 命名

### 2.4 移动端

桌面先做好。之后左侧 tab 挪到底部 + 调宽度即可。
**方法论去 Jellyfin / Jellyseerr 源码里找**——虚线卡片、季集网格他们都有成熟方案，
不要自己发明（用户明确要求：先调研轮子）。

## 三、需要后端配合的两件事

### 3.1 「应有集」数据现在全库都没有 —— 必须先加（R-F5）

实测确认：
- `works` 表只有 `title / original_title / year / media_type / origin_lang / overview / poster_path / chinese_titles / provider_ids`
- **没有季集表**
- 旧 `episodes` 表也只记磁盘上有的集（`path NOT NULL`），同样没有"本来有几集"

裁决：**识别时顺便把 TMDB 的季集表存下来**（加一张表 + 改识别流程）。
理由：识别本来就在调 TMDB，顺手多存一份；之后媒体库页完全走本地库、不依赖网络、不耗配额。

### 3.2 SSE 推送（R-F6）

活动页要"像 Steam 一样动"，15 秒轮询太钝。前后端同实例，SSE 更顺滑。
用户原话：「我并不在乎所用技术，我只在乎目的是否达成。」

## 四、设置区：不重写，做减法

### 4.1 现有分层其实是对的（实测确认，与用户直觉相反）

| | 有哪些 | 谁赢 | 能否热改 |
|---|---|---|---|
| **部署层**（env） | API key、端点、端口、缓存目录、`FFPROBE_PATH` | **env 赢**（`secrets.ts:39-41`） | 不能，要重启容器 |
| **行为层**（`settings` 表，9 键） | 目标语言、开不开 AI 翻译、扫描间隔、发动机总开关、免费源开关 | **UI 赢** | **能，下一轮巡检立刻生效** |

关键：那 9 个行为层键**根本不在 env 里**，所以不存在"谁覆盖谁"的冲突。
用户担心的"改了就要重构容器"只对部署层成立——而换 API key / 换端点本质上就是重新部署。

live test 实证：`engine_enabled` / `ai_translate_enabled` 改完下一轮立刻生效，全程没重启。

### 4.2 `MEDIA_ROOTS` 是唯一两边都能写的坑 —— 已裁决（R-F7）

live test 实际踩到：我把 DB 里的守备目录删空后，**env 又把它种回来了**，
于是扫了整个 NAS 全库（492 行入库）。

**裁决**：env 只在"数据库里一条都没有"时当种子；
**一旦用户在 UI 里动过（哪怕删空），就再也不看 env**。需要一个"已初始化过"的标记。

用户补充：**所有潜在守备目录的根，在构建容器时就要设置好**（挂载进容器那一层），
UI 里配的是这个根之下的子目录。

### 4.3 守备目录的输入方式改成"输入框 + 强制测试"（R-F8）

**不要**点击式目录选择器。改成：
1. 用户手输路径（`/xx/xx` 形态）
2. **必须点一次「测试」**，确认路径真实存在（且可写）
3. 只有测试通过才允许保存

### 4.4 33 个 env 字段全铺在设置页 = 把心血当成果展示（R-F9）

实测清点：`DEPLOY_NONSECRET_KEYS` 25 个 + `DEPLOY_SECRET_KEYS` 8 个 = **33 个环境变量全铺在设置页上**，
包括 `TRUST_PROXY` / `LOG_RETAIN_DAYS` / `TMDB_PROXY_URL` / `REALIGN_ARCHIVE_ROOT` / `FFPROBE_PATH`
——用户一辈子不会碰、看到只会焦虑。

代码注释里的动机是好的（`TRUST_PROXY` 那条写着「避免'配了但不知道生没生效'的黑盒」），
**但对象错了**：那是给排障的人看的，不是给用户看的。

用户原话：
> 「把一切事无巨细全都体现在设置页了，给人感觉就很不友好。这就是之前 agent 做的错事，
> 为了体现这项目有多困难、我们有多辛苦，把这些心血展示在了前端，而这完全会是反效果。」

**改法（减法，不是重写）**：
```
① 用户真会调的（明面上，就几个）
   目标语言 / 开不开 AI 翻译 / 守备目录 / 发动机开关
② 装的时候配一次就不看（折叠区，只读）
   API key 配了没有、LLM 端点、端口、缓存目录
③ 排障才看的（收进诊断，或干脆只留 doctor 按钮）
   TRUST_PROXY / FFPROBE_PATH / LOG_RETAIN_DAYS / 那 20 个旋钮
```
第三层的正确形态**不是 33 个字段列表，而是一个 doctor 按钮**——
live test 里我就是靠 `doctor` 一条命令定位到"三个守备目录不可写 + 容器版本过旧"的，
它比 33 个字段有用得多。

## 五、⭐ 贯穿性教训（用户点名要记下来）

> 「不能为了用户本来自己仔细点就可以解决的问题，把自己折腾得鸡飞狗跳。」

**这是本轮重构最贵的一条教训，且有两个各自付了代价的实例：**

1. **守备目录的点击式选择器** —— 为了让用户不必手输路径，做了一整套目录浏览 API +
   前端树形选择器。而正确做法是"输入框 + 让用户点一次测试"。
2. **我在 live test 里为 115 反复试探** —— 为了自动摸清"能不能写"，
   在几分钟内对 115 API 打了几十次请求，**触发阿里云 WAF 风控**，
   直接导致当晚 115 不可用、改用 NAS。正确做法同样是"探一次 → 报告给用户 → 让用户确认"。

两件事同一个形状：**替用户承担本该由用户确认的判断，成本反而更高。**

设计新前端时对每个"贴心"功能都要问一遍：
**这是在省用户一次点击，还是在替用户做他本该自己确认的判断？**
后者一律不做。

## 六·五、轮子调研结论（2026-08-11）

用户要求「先调研轮子，别自己发明」。结论如下。

### SSE：确认可用，但有一条硬限制要设计进去

2026 年的共识是「一方向推送 → SSE，双向 → WebSocket，30s 以上才更新 → 轮询」。
浏览器 `EventSource` **自带重连 + `Last-Event-ID` 续传**，认证走标准 HTTP 头，
不需要像 WebSocket 那样自己写重连。

⚠️ **HTTP/1.1 每源只有 6 个连接上限**（HTTP/2 下约 100）。
三个页面各开一条 SSE 就吃掉一半配额，再叠加图片加载会卡住整个页面。

**设计约束**：**全站只开一条 SSE 连接**，放在 shell 层，按 `event:` 类型分发到各页面。
不要每个页面各自 `new EventSource()`。

### Jellyfin 的「缺失集」：值得抄形态，但要避开它的坑

Jellyfin 有 `Missing Episode Fetcher`（抓 TMDB/TVDB 的季集表）+ 用户侧
`Display missing episodes within seasons` 开关。形态与 R-F5 一致，证明这条路走得通。

**但搜索结果里一半是用户在问「我不想看到没有的集，怎么关掉」**
（r/jellyfin 多帖、jellyfin#10725、androidtv#3717、roku#782）。
原因是它把「缺失集」做成了**全局开关 + 需要重刷元数据**，用户开关一次要等一次全库重扫，
而且各客户端行为不一致（web 遵守设置、TV 端无视）。

**我们的规避**：虚线卡片是媒体库页的**固有形态**（那正是这个页面存在的理由——
展示应有 vs 实有），不做全局开关、不需要重刷元数据。用户不想看虚线时，
本质诉求是"我不关心这部剧的完整度"，那属于**忽略某部作品**，不是"关掉一个显示选项"。

另注意 jellyfin#13997 / #16061 两个真实事故：**同名目录（含不可见空格差异）会让季分组炸掉**。
这与 R-F2「不管来源、按 work_id 合并」是同一个问题的两面——我们靠 work_id 合并天然免疫，
但前提是识别成功；识别失败的孤儿按 R-F2 不露出，正好绕开。

### Jellyseerr/Seerr：通知模型不适合我们，别抄

它的通知是**外发**的（Email / Discord / Telegram / Webhook / Web Push），
核心场景是"多用户请求 → 管理员审批 → 通知请求者"。

我们是单用户、无审批、无请求——**通知页是站内成果流水，不是外发通知系统**。
它唯一值得借鉴的是「Incredibly simple request management UI. Don't dig through the app」
这条产品主张，与用户"前端只做监视"的定位一致。

**不要引入通知 agent 体系**（那是 9 种外发渠道的配置地狱，正是 R-F9 要避免的东西）。
