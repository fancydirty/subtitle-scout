## 零、为什么先不删旧前端

现有 `web/` 是 2.5 万行 / 210 文件 / 9 个功能区。实测清点后：**真正坏的只有约 4000 行**
（library 读旧表显示假数据、redispatch 假按钮、activity 的秒表空转），
其余 2 万行（settings / setup / auth / components / i18n）是**能用的资产**，
且 live test 全程都在用它们（改配置、看部署状态、apiKey 鉴权）。

先删 = 把还能用的 2 万行一起扔掉 + 失去改配置的界面 + 讨论新设计时没有参照物。
**顺序：先讨论清楚 → 边做边替换 → 全替换完再删旧代码。**

## 二、三个页面

### 2.1 活动页 —— 像 Steam 下载页

- 两个 tab：**字幕** / **翻译**
- 每个 tab 内分两段：**正在跑** / **已排队**
- **粒度 = 作品，不是集**（R-F4）。后端工作台本来就按作品取件，
  正在跑的那个可以显示"第 3/8 集"，队列里只显示"作品 + 这轮几集"
- **识别不进活动页**（R-F1）：它虽然用 agent 但耗时很短，不值得占一个 tab

### 2.2 通知页 —— 完成的成果

- 「XX 剧找到了 S01 的第 3/5/7 集」；电影就是「已找到字幕」
- **保留一周**（R-F3）。倒序流水，**不做已读状态**（少一个状态少一堆 bug）

### 2.3 媒体库页 —— 应有集 vs 实有集 vs 字幕情况

- 小卡片网格：**实线 = 实有集**，**虚线 = 应有但磁盘上没有**
- 右上角小圆点表示字幕状态：
  - 无点 = 没有中文字幕
  - **蓝点** = 内嵌中文轨（不需要处理）
  - **绿点** = 本项目配上的
- **不管来源，按充分必要条件算**（R-F2，防猴子用户）：
  两个「绝命毒师」目录，只要有**一处** S01E03 有字幕，媒体库就显示这一集已获取
  —— 即使另一处那份仍要单独去配。合并键 = `work_id`（TMDB id）
- **识别失败的孤儿不露出**：那是用户的命名问题，底线是按 `title (year)` 命名

### 2.4 移动端

桌面先做好。之后左侧 tab 挪到底部 + 调宽度即可。
**方法论去 Jellyfin / Jellyseerr 源码里找**——虚线卡片、季集网格他们都有成熟方案，
不要自己发明（用户明确要求：先调研轮子）。

## 三、需要后端配合的两件事

### 3.1 「应有集」数据现在全库都没有 —— 必须先加（R-F5）

实测确认：
- `works` 表只有 `title / original_title / year / media_type / origin_lang / overview / poster_path / chinese_titles / provider_ids`
- **没有季集表**
- 旧 `episodes` 表也只记磁盘上有的集（`path NOT NULL`），同样没有"本来有几集"

裁决：**识别时顺便把 TMDB 的季集表存下来**（加一张表 + 改识别流程）。
理由：识别本来就在调 TMDB，顺手多存一份；之后媒体库页完全走本地库、不依赖网络、不耗配额。

### 3.2 SSE 推送（R-F6）

活动页要"像 Steam 一样动"，15 秒轮询太钝。前后端同实例，SSE 更顺滑。
用户原话：「我并不在乎所用技术，我只在乎目的是否达成。」

## 四、设置区：不重写，做减法

### 4.1 现有分层其实是对的（实测确认，与用户直觉相反）

| | 有哪些 | 谁赢 | 能否热改 |
|---|---|---|---|
| **部署层**（env） | API key、端点、端口、缓存目录、`FFPROBE_PATH` | **env 赢**（`secrets.ts:39-41`） | 不能，要重启容器 |
| **行为层**（`settings` 表，9 键） | 目标语言、开不开 AI 翻译、扫描间隔、发动机总开关、免费源开关 | **UI 赢** | **能，下一轮巡检立刻生效** |

关键：那 9 个行为层键**根本不在 env 里**，所以不存在"谁覆盖谁"的冲突。
用户担心的"改了就要重构容器"只对部署层成立——而换 API key / 换端点本质上就是重新部署。

live test 实证：`engine_enabled` / `ai_translate_enabled` 改完下一轮立刻生效，全程没重启。

### 4.2 `MEDIA_ROOTS` 是唯一两边都能写的坑 —— 已裁决（R-F7）

live test 实际踩到：我把 DB 里的守备目录删空后，**env 又把它种回来了**，
于是扫了整个 NAS 全库（492 行入库）。

**裁决**：env 只在"数据库里一条都没有"时当种子；
**一旦用户在 UI 里动过（哪怕删空），就再也不看 env**。需要一个"已初始化过"的标记。

用户补充：**所有潜在守备目录的根，在构建容器时就要设置好**（挂载进容器那一层），
UI 里配的是这个根之下的子目录。

### 4.3 守备目录的输入方式改成"输入框 + 强制测试"（R-F8）

**不要**点击式目录选择器。改成：
1. 用户手输路径（`/xx/xx` 形态）
2. **必须点一次「测试」**，确认路径真实存在（且可写）
3. 只有测试通过才允许保存

### 4.4 33 个 env 字段全铺在设置页 = 把心血当成果展示（R-F9）

实测清点：`DEPLOY_NONSECRET_KEYS` 25 个 + `DEPLOY_SECRET_KEYS` 8 个 = **33 个环境变量全铺在设置页上**，
包括 `TRUST_PROXY` / `LOG_RETAIN_DAYS` / `TMDB_PROXY_URL` / `REALIGN_ARCHIVE_ROOT` / `FFPROBE_PATH`
——用户一辈子不会碰、看到只会焦虑。

代码注释里的动机是好的（`TRUST_PROXY` 那条写着「避免'配了但不知道生没生效'的黑盒」），
**但对象错了**：那是给排障的人看的，不是给用户看的。

用户原话：
> 「把一切事无巨细全都体现在设置页了，给人感觉就很不友好。这就是之前 agent 做的错事，
> 为了体现这项目有多困难、我们有多辛苦，把这些心血展示在了前端，而这完全会是反效果。」

**改法（减法，不是重写）**：
```
① 用户真会调的（明面上，就几个）
   目标语言 / 开不开 AI 翻译 / 守备目录 / 发动机开关
② 装的时候配一次就不看（折叠区，只读）
   API key 配了没有、LLM 端点、端口、缓存目录
③ 排障才看的（收进诊断，或干脆只留 doctor 按钮）
   TRUST_PROXY / FFPROBE_PATH / LOG_RETAIN_DAYS / 那 20 个旋钮
```
第三层的正确形态**不是 33 个字段列表，而是一个 doctor 按钮**——
live test 里我就是靠 `doctor` 一条命令定位到"三个守备目录不可写 + 容器版本过旧"的，
它比 33 个字段有用得多。

## 五、⭐ 贯穿性教训（用户点名要记下来）

> 「不能为了用户本来自己仔细点就可以解决的问题，把自己折腾得鸡飞狗跳。」

**这是本轮重构最贵的一条教训，且有两个各自付了代价的实例：**

1. **守备目录的点击式选择器** —— 为了让用户不必手输路径，做了一整套目录浏览 API +
   前端树形选择器。而正确做法是"输入框 + 让用户点一次测试"。
2. **我在 live test 里为 115 反复试探** —— 为了自动摸清"能不能写"，
   在几分钟内对 115 API 打了几十次请求，**触发阿里云 WAF 风控**，
   直接导致当晚 115 不可用、改用 NAS。正确做法同样是"探一次 → 报告给用户 → 让用户确认"。

两件事同一个形状：**替用户承担本该由用户确认的判断，成本反而更高。**

设计新前端时对每个"贴心"功能都要问一遍：
**这是在省用户一次点击，还是在替用户做他本该自己确认的判断？**
后者一律不做。

## 六·五、轮子调研结论（2026-08-11）

用户要求「先调研轮子，别自己发明」。结论如下。

### SSE：确认可用，但有一条硬限制要设计进去

2026 年的共识是「一方向推送 → SSE，双向 → WebSocket，30s 以上才更新 → 轮询」。
浏览器 `EventSource` **自带重连 + `Last-Event-ID` 续传**，认证走标准 HTTP 头，
不需要像 WebSocket 那样自己写重连。

⚠️ **HTTP/1.1 每源只有 6 个连接上限**（HTTP/2 下约 100）。
三个页面各开一条 SSE 就吃掉一半配额，再叠加图片加载会卡住整个页面。

**设计约束**：**全站只开一条 SSE 连接**，放在 shell 层，按 `event:` 类型分发到各页面。
不要每个页面各自 `new EventSource()`。

### Jellyfin 的「缺失集」：值得抄形态，但要避开它的坑

Jellyfin 有 `Missing Episode Fetcher`（抓 TMDB/TVDB 的季集表）+ 用户侧
`Display missing episodes within seasons` 开关。形态与 R-F5 一致，证明这条路走得通。

**但搜索结果里一半是用户在问「我不想看到没有的集，怎么关掉」**
（r/jellyfin 多帖、jellyfin#10725、androidtv#3717、roku#782）。
原因是它把「缺失集」做成了**全局开关 + 需要重刷元数据**，用户开关一次要等一次全库重扫，
而且各客户端行为不一致（web 遵守设置、TV 端无视）。

**我们的规避**：虚线卡片是媒体库页的**固有形态**（那正是这个页面存在的理由——
展示应有 vs 实有），不做全局开关、不需要重刷元数据。用户不想看虚线时，
本质诉求是"我不关心这部剧的完整度"，那属于**忽略某部作品**，不是"关掉一个显示选项"。

另注意 jellyfin#13997 / #16061 两个真实事故：**同名目录（含不可见空格差异）会让季分组炸掉**。
这与 R-F2「不管来源、按 work_id 合并」是同一个问题的两面——我们靠 work_id 合并天然免疫，
但前提是识别成功；识别失败的孤儿按 R-F2 不露出，正好绕开。

### Jellyseerr/Seerr：通知模型不适合我们，别抄

它的通知是**外发**的（Email / Discord / Telegram / Webhook / Web Push），
核心场景是"多用户请求 → 管理员审批 → 通知请求者"。

我们是单用户、无审批、无请求——**通知页是站内成果流水，不是外发通知系统**。
它唯一值得借鉴的是「Incredibly simple request management UI. Don't dig through the app」
这条产品主张，与用户"前端只做监视"的定位一致。

**不要引入通知 agent 体系**（那是 9 种外发渠道的配置地狱，正是 R-F9 要避免的东西）。

## 六·六、SSE 事件粒度（R-F10）

用户裁决：**「对用户而言有必要推的事件才推，而非事无巨细」**，并说"作为人类没法具体说多粗"。
下面是按这条判据从现有 30 条 daemon 日志里筛出来的结果。

### 判据：站在用户视角问"我需要知道吗"

| 现有日志 | 用户视角 | 推？ |
|---|---|---|
| `字幕 X (N 文件, 第 i/n 个)` | 现在在干什么 | ✅ |
| `installed N/N sidecars for X` | **找到了！** | ✅ |
| `翻译 X` / `翻译结果 installed` | 同上 | ✅ |
| `巡检开始` / `巡检完成，歇着等明天` | 系统在忙还是在歇 | ✅ |
| `scan: ...跳过删除（R8 / C47）` | **我的库可能有问题** | ✅ 异常 |
| `scan: probe wrote=N unavailable=N` | 不关心 | ❌ |
| `回填: embedded_langs ok=200` | 不关心 | ❌ |
| `judge: 判定 N 个文件` | 不关心 | ❌ |
| `trace 修剪` / `清理写探针` | 不关心 | ❌ |
| 各种 `（隔离，下轮重试）` | 单文件抖动、会自愈 | ❌ |

### 定成 4 类事件

```
activity   工作台状态变化（开始处理某作品 / 队列变化 / 巡检开始与结束）
found      找到并装上了字幕（通知页的数据源）
health     异常：守备目录读取失败、R8/C47 拦截、provider 全挂
progress   正在处理的那一个作品的进度（第 3/8 集）—— 唯一的高频事件
```

### 三条约束

1. **只推变化，不推心跳**。日巡检模型下大部分时间没有变化，没变化就不发。
   连接保活用 SSE 注释帧（`: ping`），不占事件通道。
2. **`progress` 要节流**（每秒最多 1 次）。它是唯一可能高频的事件——
   一部剧 24 集逐集完成时会连发。其余三类天然低频，不节流。
3. **全站一条连接**（见 §六·五 的 HTTP/1.1 六连接上限），
   放 shell 层按 `event:` 分发，页面订阅自己关心的类型。

### 反面清单（明确不推）

排障类信息一律不进 SSE：probe 统计、回填进度、judge 计数、trace 修剪、单文件隔离错误。
它们的正确去处是 **doctor 按钮 + 日志文件**（同 R-F9 的三层分区：排障归排障）。

理由与 R-F9 同源：**把系统的辛苦展示给用户看，是反效果**。用户要的是"找到了什么"，
不是"我跑了多少次 ffprobe"。

## 六·七、后端前置：三件已完成（2026-08-11）

前端要的数据以前拿不到。三件前置做完了，**都在生产验证过**。

### ① 应有集（R-F5）— `d302c22`

⚠️ **我给的前提是错的，subagent 实测纠正**：我说"全库没有季集表、要新建表加迁移"，
实际 `tmdb_seasons` **早在 v12 就建好**（注释还写着"spec §8.1 应有集缓存"），
读写函数（`getSeasonTable` / `getSeasonEpisodes` / `refreshSeriesCatalog` / `canonicalEpisodes`）
全都有，**零迁移**。

**真实缺口是第 6 例同型缺陷，且形态更隐蔽**：表有、写入方有、读出方有——
唯独**没人触发**。它的触发条件长在 `series` 表上（`server.ts` 的 `librarySeriesDetail`
先查 `SELECT … FROM series`），而新架构一行都不写那张表。
生产实测坐实：`series` **0 行** / `works` **110 行** / `tmdb_seasons` **0 行**。

前 5 次是"写了列没定谁写"，这次是"写入方存在，但它的开关长在一张没人填的表上"。

修法：照 `backfillProviderIds` 的形态加 boot 回填 pass（200 行/轮上限、try/catch 隔离、
`WHERE media_type='tv'` 在谓词层滤掉电影、抓失败一行不落）。
**生产实测**：68 部剧 / **2144 集** 填入，零失败。媒体库页的核心数据一条 SQL 就能出：
```
Three Kingdoms  S1   应有 95 / 实有 95   ← 完整
Re:ZERO         S1   应有 85 / 实有 77   ← 缺 8 集 → 8 个虚线卡片
```

### ② SSE 推送通道（R-F10）— `32ceaeb`

新总线 `src/core/scoutEvents.ts` + 端点 `GET /api/v2/events`。11 个 emit 接线点。

三个设计要点：
- **显式 emit 而非解析日志**：本仓同一天栽过两次"日志文案与实际口径不符"，
  把日志当 API 就是把事件通道建在流沙上
- **不复用既有的 `traceBus`**：那是 agent 工具调用流水（事无巨细），
  与"该不该推给用户"这条判据无处安放
- **被节流折叠的 progress 不占 id、不进缓冲**：占号会让重连补发看到 id 空洞
  （客户端无从判断是丢了还是没发生过），进缓冲则是"推不出去的东西重连后诈尸"

生产验证：`200 / text/event-stream / no-cache`，无事件时只发注释帧。

### ③ 通知流水表（R-F3）— `3ea0c7d`

**上一件的 subagent 发现的缺口**：SSE 的续传缓冲是**进程内环形缓冲（50 条、非持久）**，
而 R-F3 要求保留一周 → **用户关着浏览器的那 23 小时里找到的字幕全部丢失**，容器重启同样清零。
所以通知页**不能只靠 SSE**，必须有持久化数据源。

四个候选逐个实测排除，其中一条是决定性的：
**`files.updated_at` 推不出通知流水**——`observeSubtitle` 每轮 B 档复核（7 天一次）
无条件重写 `sub_status='covered', updated_at=?`。三个月前配上字幕的文件每周被刷一次，
照它做一周窗会天天冒出陈年老片假装"刚找到"；更糟的是**真·新成果与假·复核刷新在这一列上完全同形**。

设计要点：
- 逐集存、读时聚合（存聚合撞"同一季分两次找到"）
- **唯一索引走 `ifnull()`**：SQLite 视 NULL 互不相等，电影 `season/episode` 恒 NULL →
  裸 UNIQUE 对电影完全失效而剧集那一半照常生效 ⇒ 只测剧集会全绿而电影刷屏（同 `jobs_identity` 的既有坑）
- 幂等 = 刷新而非追加（重复装盘的三种成因都不是新成果；追加会让"每天被重找一次"的文件一周灌 7 条同文，而 R-F3 明令不做已读状态、用户无从清理）
- 读窗 `>` 与清理 `<=` **严格互补**（都用开区间会在 `now-7天` 留一行"读不到又删不掉"的幽灵行，永远占着幂等键让那一集再也发不出新通知）

清理挂在 `dbMaintenance` 末尾（那个循环已在跑 VACUUM/checkpoint），不新起定时器。

**生产状态**：schema v33、通知表已建、SSE 活着、季集 2144 行、covered 167。

### ④ 媒体库页数据端点（R-F2 + R-F5）— `bce8eef`

新建 `GET /api/v2/mediaLibrary` + `/:workId`，**旧的 4 个 builder 原样不动**（前端替换完再删）。
不原地改是因为旧 `LibraryItemDTO` 背着为旧模型设计的字段（`job` 挂已死的 jobs 表、
`coverage` 是六桶旧覆盖率模型），原地改会让 DTO 同时背两套语义。

⚠️ **我说"中文判定复用 `langOf`"是不够的，subagent 实测纠正**：
```
chi/zho/zh/zh-Hant  → langOf 返回 zh   ✅
chs / cht           → langOf 返回自身  ❌  （只折叠 ZH_ORIGIN_CODES={zh,cn,chi,zho,cmn}）
```
只用 `langOf` 会让**带简繁内嵌轨的片子丢掉蓝点**。正解是两臂并列
（`tagsForLanguage('zh')` 命中 ∨ `langOf === 'zh'`）。反向验证时精准红 2 条，正是 chs/cht。

**R-F2「不管来源」的实现**：跨该格全部文件求或（`.some()`），绝不取首行。
同时 `fileCount`/`subtitledFileCount` 如实呈报——"另一处那份仍要单独去配"这个事实
不许被聚合吞掉。列表页的 `onDiskEpisodeCount` 用去重后格数而非 `COUNT(*)`：
两个目录各一份时后者会把"实有 1 集"报成 2 集。

**不保留 `section`（动漫分区）**：`genres` 列只在 `series` 表上（v13 加的），
`works` **没有这一列**，第一臂结构上不可用；且 R-F2 的形态是网格+圆点，没有分区概念。

### R-F11 视觉基准 = Linear DESIGN.md

来源 `VoltAgent/awesome-design-md`（107k★）的 `design-md/linear.app/DESIGN.md`，
已落项目根目录 `DESIGN.md`（commit `084b7bc`）。选它因为深色 + 密集 + 开发者工具 + 状态标记多。

它给出的关键规范**直接解释了我前几版稿子为什么"素"**：

而我之前只用了一层背景 + 一层边框。真实 token：

### R-F12 集号染色替代圆点（媒体库页）

⚠️ **原方案（三色小圆点）被调研推翻**：Carbon Design System 要求状态指示必须用
**颜色 + 形状/符号至少两者**——只靠颜色对色盲无效、对屏幕阅读器不可见。

用户否掉的中间方案：左竖线（Bootstrap alert 遗产，土）。
查 Linear 的 DESIGN.md 确认**它根本不用左竖线**，它的 status-badge 靠药丸 + 底色。

**最终选定：状态直接长在集号上**——`E01 ✓`（绿）/ `E02 ◆`（蓝）/ `E03 ···`（灰）。
mono 字体 + 状态色，读起来像终端输出。这是唯一**零额外元素**的方案：
状态和本来就要显示的编号合二为一，一屏 40 张卡也不碎。

### R-F13 全背景式卡片（活动页）

演进路径：纯文字列表 → 卡片里放缩略图 → **图本身就是卡片**。

最终形态：**左侧图铺满，横向渐变渐隐进 surface-1 实色，文字浮在渐隐区。**
```css
/* 在跑的：横版 backdrop 占 60% */
background: linear-gradient(to right,
  rgba(1,1,2,.06) 0%, rgba(1,1,2,.28) 20%, rgba(1,1,2,.84) 44%, #0f1011 60%);
/* 排队的：竖版 poster 59px 宽，渐变区 118px（图的两倍） */
background: linear-gradient(to right,
  rgba(1,1,2,0) 0%, rgba(1,1,2,.14) 44%, rgba(1,1,2,.78) 68%, #0f1011 100%);
```

三个关键决定：
1. **渐变终点用 surface-1 实色，不是半透明黑**——右半区底色与普通卡片完全一致，
   文字对比度稳定，不会因背后有图而发飘
2. **在跑用横版 backdrop、排队用竖版 poster**——用户实测发现矛盾的根源是宽高比：
   `16:9 @ 70px高 = 124px宽`（太窄看不清）vs `2:3 @ 70px高 = 47px宽`（天生适合窄行）。
   两个位置职责不同，形状不同不是缺陷是分工
3. **排队行 88px 高 + 标题 16px**——行高撑起来右侧才不显空。副标题合并成
   「2018 · 动画 · 13 集待处理」一行说完

调研到的共同规范（Plex/Jellyfin/Poster Tools 都遵守）：
> dark matte + gradient keep text crisp over busy art

## 六·九、⭐ 目标语言可切换性（R-F15，用户点名的架构级缺口）

用户原话：
> 「本来就是目标语言字幕的语言影视……咱们这个项目之所以没有硬编码锚定中文，
> 就是因为要考虑用户不止中国人，可能会是美国人想要英文字幕的情况。」
> 「关于资源的字幕情况，需要在一开始就记录下来，每个资源有哪些字幕，
> 这样在用户更换目标语言后，数据库能反应过来。」

这不是 UI 标记问题。查代码确认**两个架构级缺口**：

### 缺口 ① `verdict.reason` 算出来就被扔掉

`judgeSubtitle` **已经返回** `reason`（`origin-skip` / `embedded` / `missing`），
但 `daemonV2.ts:903` 只用了 `verdict.needs`，reason 直接丢弃，`files` 表也没有这一列。

后果：生产库 1026 个 `needs_subtitle=0` 的文件，**分不出哪些是"本来就是目标语言"、
哪些是"有内嵌字幕"**。第三种 UI 标记拿不到数据。

### 缺口 ② 外挂字幕的语言从没被记录

`findExternalSidecar` 返回 `{ path, language }`，但 `observeSubtitle` **只用它判断"有没有"**，
language 丢弃，只写无语言的布尔 `sub_status='covered'`。

更关键：它**只搜当前目标语言的标签**。片子旁边有 en/ja/ko 三条字幕、目标是 zh 时，
系统完全不知道那三条存在。

### 换目标语言时的真实后果（修复前）

| 情况 | 结果 |
|---|---|
| 国产剧（origin=zh → 改目标 en） | ✅ 重判正确 |
| 有内嵌中文轨 | ✅ 重判正确 |
| **磁盘上早有 `.en.srt`** | ❌ 系统不知道它存在，会**重新找一遍**（烧钱） |
| **已配 `.zh-Hans.srt`** | ❌ `covered` 是无语言布尔，改目标后**它还是 covered**（显示错误） |

### 要补的三件（用户已裁决全做）

1. **`files` 加 `skip_reason` 列** —— 把已算出的 `verdict.reason` 存下来。改动极小
2. **扫描时记录全部外挂字幕语言** —— 不只搜目标语言，`<stem>.*.srt/ass` 全扫，
   语言集合存成 JSON（如 `["zh-Hans","en","ja"]`）
3. **换目标语言 → 触发全库重判** —— 清 `needs_subtitle` / `sub_status` 让下轮巡检重判。
   有了第 2 条的数据，重判**不需要重新扫盘**

### 媒体库页第三种标记

```
E01 ✓    绿   已配字幕（本项目找到的）
E02 ◆    蓝   内嵌字幕（片源自带轨）
E03 ◇    灰   原生同语言（片子本来就是这语言）  ← 新增
E04 ···  灰   待处理
```

第三种用**空心菱形 ◇ + 中性灰**：与内嵌的实心 ◆ 呼应（都是"不用管"），
但灰色说明它不是靠字幕解决的、是**压根不需要**。形状与颜色双通道，符合 Carbon 规则。
