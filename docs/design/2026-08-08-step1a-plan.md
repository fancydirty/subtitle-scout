## 二、Task 拆分（每个 task 独立 TDD，完成后起子代理审校）

### Task 1a-1：`findOverlappingRoot` 下移到 settingsRepo，apiV2 改 import

**动机**：一份实现，两处使用。为 Task 1a-2 提供地基。

**改动**：
- `settingsRepo.ts` 导出 `findOverlappingRoot(candidate, existing)`
- `apiV2.ts` 删除本地定义，改 `import { findOverlappingRoot } from '../v2/settingsRepo.js'`
- 保持函数签名与返回值 `{ root, relation: 'parent' | 'child' } | null` 完全一致

**TDD 用例**（新建 `settingsRepo.overlap.test.ts`）：
1. 候选是既有根的子目录 → `{ root, relation: 'child' }`
2. 候选是既有根的父目录 → `{ root, relation: 'parent' }`
3. 候选与既有根相等 → `null`（幂等交给 addRoot，非重叠）
4. 无重叠 → `null`
5. 同名前缀不误判：`/media/tv2` vs 既有 `/media/tv` → `null`（防 `startsWith` 陷阱）
6. 多个既有根时返回**第一个**命中的（错误文案要指名道姓）

**验收**：apiV2 既有测试全绿（证明下移无行为变化）+ 新增 6 条绿。

### Task 1a-2：`addRoot` 加嵌套检测门，封堵 seedRootsFromEnv 旁路

**动机**：D7 本体。这是防 C29 删库的地基。

**改动**：
- `addRoot` 内部先查既有根，命中重叠则**拒绝**
- 拒绝的表达方式：**返回值改为 `{ ok: true } | { ok: false; conflict: {root, relation} }`**
  （不抛异常——`seedRootsFromEnv` 批量种入时单条冲突不应中断整批）
- `seedRootsFromEnv` 逐条调 `addRoot`，冲突的**跳过并收集**，返回 `{ seeded, rejected }`
- `apiV2` 的调用点适配新返回值（它本来就有自己的检测，现在变成双保险；
  错误文案沿用既有的"跟哪个根撞了"）

**破坏性**：`addRoot` 返回值从 `void` 变成对象 → 所有调用方需适配。
先查全部调用方，逐个改。

**TDD 用例**：
1. addRoot 拒绝子目录嵌套 → `{ok:false, conflict:{relation:'child'}}`，且**表里没有新行**
2. addRoot 拒绝父目录嵌套 → `{ok:false, conflict:{relation:'parent'}}`，表里无新行
3. addRoot 重复同一路径 → `{ok:true}`（幂等，`added_at` 不刷新——既有语义不破）
4. addRoot 正常新增 → `{ok:true}`，表里有新行
5. `seedRootsFromEnv` 中一条冲突 → 该条跳过、**其余正常种入**，返回 rejected 含冲突项
6. `seedRootsFromEnv` 全部冲突 → 全跳过，不抛异常
7. `seedRootsFromEnv` 在 `media_roots` 非空时仍是空操作（既有语义不破）

**验收**：全部调用方编译通过 + 既有 settingsRepo 测试全绿 + 新增 7 条绿。

### Task 1a-3：存量嵌套配置启动告警

**动机**：D7 附加。存量库可能已有嵌套配置（历史遗留），Task 1a-2 只挡新增。
**不自动删**（用户的守备目录配置不该被程序擅自改），只报警。

**改动**：
- `settingsRepo` 加 `detectNestedRoots(): Array<{root, nested, relation}>`
- 在 daemon 启动路径调用并 log 告警（含"D1 删除逻辑会误删子根"的明确警示）
- 放在 `watchStartupWarnings.ts`（已有的启动告警收口处，符合既有约定）

**TDD 用例**：
1. 无嵌套 → 返回空数组
2. 存在 `/media` + `/media/tv` → 返回一条，relation 正确
3. 三层嵌套 `/a` + `/a/b` + `/a/b/c` → 返回全部成对关系
4. 启动告警包含冲突路径与警示语（断言 log 内容）

**验收**：新增 4 条绿 + 手动确认告警文案可读。

### Task 1a-4：`removeRoot` 补 files 清理（D11 / C33）

**动机**：D11 本体。root 移除时 files 行必须一起清，否则成为孤儿——
识别流会永远为不存在的文件跑 agent（C18 幽灵队列）。

**改动**：
- 在 `removeRoot` 的既有事务内，加 `DELETE FROM files WHERE substr(path,1,length(?)) = ?`
- 沿用既有的 `prefix = root + '/'` 变量与 substr 匹配法（**不用 LIKE**——
  媒体路径可含 `%` `_`，既有注释已论证）
- 返回值加 `files: number` 计数
- 位置：放在旧表清理**之后**、`DELETE FROM media_roots` **之前**（同一事务内顺序无关，
  但保持"先清数据行、最后清根登记"的既有叙事）

**TDD 用例**（**必须走 `removeRoot` 真实入口，不许直接 SQL** / D11 铁律）：
1. removeRoot 后该根下 files 行被清除，返回 `files` 计数正确
2. **其他根下的 files 行不受影响**（前缀隔离）
3. 同名前缀不误伤：移除 `/media/tv` 不动 `/media/tv2` 下的 files 行
4. 路径含 `%` 或 `_` 的目录能正确清理（`100% Pascal-sensei` / `Look_Back`，防 LIKE 陷阱）
5. 不存在的 root → 返回 null，**files 表零改动**（既有存在性守卫不破）
6. files 与旧表在**同一事务**：模拟中途失败 → 全部回滚（无半清状态）

**验收**：新增 6 条绿 + 既有 removeRoot 测试全绿（证明旧表清理行为未变）。

## 四、自审：这个计划有什么风险

**风险 1：Task 1a-2 的返回值变更是破坏性的**
→ 缓解：先 grep 全部 `addRoot` 调用方，逐个适配后再改实现。

**风险 2：settingsRepo 既有 1 红可能与本次改动重叠**
→ 缓解：动手前先跑一次 settingsRepo 测试，记录那条红的具体内容作为基线。

**风险 3：`findOverlappingRoot` 下移后 apiV2 的错误文案可能变**
→ 缓解：Task 1a-1 只搬函数不改逻辑，apiV2 既有测试必须全绿才算过。

**风险 4：Task 1a-4 加 files 清理时，如果 files 表在某些测试库里不存在会炸**
→ 缓解：files 表在 v30 schema 已建（已核实），且 `openDb` 统一建表；测试用 `:memory:` 走同一 schema。

**风险 5（真实存在，需提前说明）**：Task 1a-3 只告警不自动修。
若用户存量确有嵌套配置，D1 删除逻辑（第 1b 步）上线时**仍会删错**。
→ 处置：第 1b 步的删除逻辑必须**主动跳过被嵌套关系污染的根**，不能只依赖 1a-3 的告警。
这一条要写回 spec 的第 1b 步（本计划执行完顺手补）。
