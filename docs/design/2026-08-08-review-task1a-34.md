## 🔴 F7：`normalizeRoots()` 在两个别名映射到同一规范形态时**抛 UNIQUE 约束、整个事务回滚**

**证据**：`src/v2/settingsRepo.ts:261-285`（`normalizeRoots` 全体），关键在 `:277` 的 `canonicalExists` 判定。

```
const canonicalExists = rows.some((x) => x.path === c)
if (canonicalExists) del.run(r.path)          // 规范形态已在 → 删别名
else upd.run(c, earliest.get(c)!, r.path)     // 否则原地改写
```

**问题**：`rows` 是**事务开始时的一次性快照**（`:263`），循环内不更新。当库里有**两个不同的非规范别名**指向同一规范形态、且**规范形态本身不在库里**时：

- `rows = ['/media/tv/', '/media//tv']`，两者 `resolve()` 都是 `/media/tv`
- 第一条：`canonicalExists = rows.some(x => x.path === '/media/tv')` → **false**（快照里确实没有）→ 走 `upd`，把 `/media/tv/` 改成 `/media/tv` ✅
- 第二条：`canonicalExists` 仍查同一份**旧快照** → 仍 **false** → 也走 `upd`，`UPDATE ... SET path='/media/tv' WHERE path='/media//tv'` → **UNIQUE constraint failed: media_roots.path**

**实测**（probe P1）：

```
P1 THREW: UNIQUE constraint failed: media_roots.path
   rows = [{"path":"/media//tv",...},{"path":"/media/tv/",...}]
```

Q4 / Q5 复现同一故障（`/x//y` + `/x/y/`；三别名亦然）。Q6 反证：只要规范形态**也在库里**，三条全走 `del` 路径就没事——所以这是一个**恰好被现有 6 条测试全部绕过**的洞（测试只造了"单个别名"或"别名+规范形态并存"两种形态，从没造过"两个别名、无规范行"）。

**失效场景（用户可见，且是致命的）**：
运维在 `MEDIA_ROOTS` 里先后手抖写过 `/media/tv/` 和 `/media//tv`（或历史上通过不同途径写进库）。此后**每次 `watch` / `reconcile-all` 启动**：
1. `settingsRepo.normalizeRoots()`（`src/cli/index.ts:195` / `:276`）抛未捕获异常
2. 两处调用都是裸调用，**外面没有 try/catch**
3. → `cmdWatch()` / `cmdReconcileAll()` 直接 crash，**daemon 起不来**，且脏数据一行都没被修（事务全回滚）
4. 用户看到的是一句 `SqliteError: UNIQUE constraint failed: media_roots.path`，与"守备目录"毫无字面关联，**排查方向完全错**

这比 F2 想修的病更严重：F2 修的是"多扫一遍 + 删不掉"，F7 是**启动即死锁死循环**（重启也修不好，因为每次都在同一步炸）。

**修法**（二选一，推荐前者）：
1. 循环内维护一个"已占用规范形态"的活集合，第二个别名走 `del` 而非 `upd`：
   ```ts
   const taken = new Set(rows.filter(r => resolve(r.path) === r.path).map(r => r.path))
   for (const r of rows) {
     const c = resolve(r.path)
     if (c === r.path) continue
     if (taken.has(c)) del.run(r.path)
     else { upd.run(c, earliest.get(c)!, r.path); taken.add(c) }
   }
   ```
2. 或把 `upd` 改成 `UPDATE OR REPLACE`——但那会丢 `added_at` 语义，不推荐。

**必须补的测试**：`两个不同别名映射到同一规范形态（且规范形态不在库里）→ 归一化成一行、不抛`。这条现在会红。

## 🔴 F8：`removeRoot('/')` 时 `prefix === '/'`，把 `files` / `episodes` / `movies` / `parked_paths` **整表清光**

**证据**：`src/v2/settingsRepo.ts:374`

```
const prefix = path.endsWith('/') ? path : `${path}/`
```

`path === '/'` → `endsWith('/')` 为 true → `prefix = '/'`。而所有清理谓词都是 `substr(path,1,length(?)) = ?`（`:378/382/385/399/402/405/422/431`）——`length('/') = 1`，`substr(path,1,1) = '/'` 对**每一条绝对路径都为真**。

**实测**（probe P3 / P4）：

```
P3 root='/'，files 有 /media/tv/A.mkv 与 /data/x.mkv（后者不在任何子树内）
   result = {...,"files":2}   files left = []      ← 整表清光
P4 root='/' 与 /media/tv 并存，removeRoot('/')
   result = {...,"files":1}   roots = [/media/tv]  files = []
   ← 只删了 '/' 这一个根，但 /media/tv 的 files 行被连带清光；/media/tv 还是守备目录，
     库却空了 → 下轮全量重扫 + 全量重识别
```

**`'/'` 真的能进库吗？能，两条路都通**：
- `seedRootsFromEnv('/')`：`isAbsolute('/')` 为 true、`findOverlappingRoot` 在空库无冲突 → 实测 P5 `seeded:["/"]`
- HTTP `POST /api/v2/settings/roots` body `{path:'/'}`：同理，闸门只挡"与既有根嵌套"，空库/唯一根时 `'/'` 畅通

注意 F1 修的是"`'/'` 不再逃过嵌套闸门"（`withSep` 那个函数，`:60`），**不是**"禁止 `'/'` 作为根"。P12 确认存在性守卫会拦下"`'/'` 不是登记根"的情况——但当 `'/'` **是**登记根时守卫放行，然后前缀比较全表命中。

**关于问题里提的 `endsWith('/')` 分支还有没有用**：归一化上线后，库里的 path 都是 `resolve()` 形态，唯一还会 `endsWith('/')` 的就是 `'/'` 本身。所以这个分支现在**只服务于 `'/'` 这一个值，而且服务方式是错的**——它恰恰是让 `prefix` 退化成全表通配符的原因。这个分支不是"多余"，是"有害"。

**失效场景**：用户在 setup wizard 里为了"扫全盘"填了 `/`（Docker 里 `/` 就是容器根，`/media` 挂载在下面，这个填法完全符合直觉），或 `MEDIA_ROOTS=/`。后来他改主意，在 dashboard 里加了 `/media/tv` 再删掉 `/`——一次点击，**整个索引库被清空**：`files`、`episodes`、`movies`、`series`（空壳级联）、`parked_paths` 全没了。前端只会显示"已删除 N 集"，用户看不出这是灾难。下轮扫描会全量重识别，**烧掉整库的 TMDB + LLM 调用**。

**修法**（两层，都该做）：
1. `prefix` 计算改成 `stripTrailingSep(path) + sep` 的等价物（复用 `withSep`，`:60` 已有且已处理 `'/'`）——但 `'/' + sep` 仍是 `'/'`，`withSep('/')` 返回 `'/'`，**光改这个不够**。
2. 真正的修法：`'/'` 作为守备目录本身就该被拒（它 100% 是嵌套配置，F1 的注释自己都这么写了）。在 `addRoot` / `seedRootsFromEnv` 加一道"根目录不得作为守备目录"的门，与 `not-absolute` 同级；并在 `normalizeRoots` 或启动告警里点名存量的 `'/'`。
3. 兜底：`removeRoot` 内加断言 `if (prefix === sep) throw`（防御性，防止未来又有路径绕进来）。

**必须补的测试**：`removeRoot('/')` 不得清除不在其它逻辑子树意图内的行 / 或 `addRoot('/')` 被拒。

## 🟡 F9：`normalizeRoots()` 可能**制造出新的嵌套根**，且这条路径无人告警

**证据**：`src/v2/settingsRepo.ts:278`（`upd` 分支）——`resolve()` 会展开 `'..'`，改写后的规范形态与库里另一个根可能构成嵌套，而 `normalizeRoots` 自己不做嵌套检查。

**实测**（probe P9）：

```
库: '/media/tv/..'(300) + '/media/tv'(100)
normalizeRoots → roots = ['/media'(300), '/media/tv'(100)]
detectNestedRoots → [{root:'/media', nested:'/media/tv'}]
```

即：归一化**自己造出了一对嵌套**。

**为什么不是 🔴**：`cmdWatch` 的顺序（`src/cli/index.ts:276 → 284`）恰好是 `normalizeRoots` → `detectNestedRoots`，所以 watch 路径下这对新造的嵌套**会被告警看见**。这是接线顺序的运气，不是设计保障。

**但 `cmdReconcileAll` 路径没有告警**：`src/cli/index.ts:195` 只调 `normalizeRoots()`，**没有** `detectNestedRoots()` / `existingNestedRootsWarning()`（对比 `:284`，那是 `cmdWatch` 独有的）。`reconcile-all` 是一次性全量命令，恰恰是最可能触发 D1 式全量差集的入口，却看不到嵌套告警。

1. `cmdReconcileAll` 补上同一对 `detectNestedRoots()` + `existingNestedRootsWarning()`（两行，与 `:284-285` 对称）。
2. 更彻底：把"normalizeRoots → detectNestedRoots → warn"三步收成一个 `SettingsRepo` 上的组合方法或一个 `startupRootsHygiene()` 辅助函数，两个入口都调它——避免第三个入口（未来的 `doctor`？`src/cli/index.ts:915` 就直接 `listRoots()` 了）又漏一处。

## 🟡 F10：`normalizeRoots()` 的"补正 added_at"后置循环是**死代码**

**证据**：`src/v2/settingsRepo.ts:281-284`

```
for (const [c, at] of earliest) {
  this.db.prepare('UPDATE media_roots SET added_at = ? WHERE path = ? AND added_at > ?')
    .run(at, c, at)
}
```

**逐条验证 `AND added_at > ?` 的正确性**：语义上"只在当前值晚于最早值时才下压"是对的（幂等友好，不会把已正确的值反向改晚）。但**它永远命中 0 行**：

- `earliest` 的键是规范形态 `c`，值是"所有映射到 `c` 的行里最早的 added_at"
- 能匹配 `WHERE path = c` 的行只有两种来源：
  - (a) 快照里本来就是规范形态的行 → 它的 `added_at` **参与了 `earliest.get(c)` 的 min 计算**（`:268-272` 的循环遍历**全部** rows，不区分是否规范）→ 所以 `added_at >= at` 恒成立，`> at` 只在"有别名更早"时为真
  - (b) 被 `upd` 改写出来的行 → `upd` 已经带上了 `earliest.get(c)!`（`:278`）→ `added_at === at`，`> at` 为假

那么 (a) 的"有别名更早"呢？此时别名走的是 `del`（因为 `canonicalExists` 为 true），别名行被删、规范行 `added_at` 仍是较晚的值 → 这个后置循环**本该**在此生效。

**实测（Q1）证明它没生效，因为不需要它**：

```
Q1 库: '/media/tv'(500) + '/media/tv/'(100)   ← 别名更早、规范更晚
   normalizeRoots → [{"path":"/media/tv","addedAt":100}]   ✅ 正确
```

`addedAt` 是 100 而不是 500——但这**不是**后置循环干的。把后置循环的 `AND added_at > ?` 拿掉也是同一结果，把整个循环删掉呢？此时 (a) 分支的规范行会保留 500……

等一下。上面 Q1 的结果说明 `added_at` **确实**被下压到 100 了，而唯一能做这件事的就是这个后置循环（`del` 不改 `added_at`）。所以**这个循环不是死代码，它正是 Q1 场景的唯一正确性来源**，`AND added_at > ?` 条件也是对的（500 > 100 → 命中；Q2/Q3 场景 `at === added_at` → 不命中，幂等）。

**修正本条结论**：`AND added_at > ?` 的逻辑**正确**，后置循环**必要**，标🟡的理由降级为：

**实际问题（🟡，可读性/效率）**：`this.db.prepare(...)` 写在循环体内（`:282`），每次迭代重新 prepare 一条相同的 SQL。仓库里其它地方（`del`/`upd`/`delSub`/`delFiles`）都遵守"循环外 prepare、循环内 run"的约定。守备目录个位数所以无实际性能影响，但这是**与既有约定不一致的写法**，且 better-sqlite3 的 statement cache 之外每次都要过一遍 SQL 解析。

**修法**：把 prepare 提到循环外，与 `del`/`upd` 并列。

**另一个真问题（🟡）**：这段逻辑的**注释与实现的因果说反了**。注释说"规范形态本身的 added_at 可能晚于**被删掉的别名**"——但循环遍历的是 `earliest` 的**全部**键，包括从未有过别名的规范根，也包括刚被 `upd` 改写出来的行。对这些行它是无害 no-op，但读者要推演三种来源才能确认这一点。建议注释直接点明"只有 del 分支（别名更早 + 规范形态已在库）需要这次补正，其余两种来源恒为 no-op"。

## 🟢 F11：`detectNestedRoots()` 的去重与三层嵌套——**算法正确**，性能无问题

**证据**：`src/v2/settingsRepo.ts:303-317`。

**去重正确性（手动推演 `/a` + `/a/b`）**：
外层 `for (const a of paths)`、内层 `for (const b of paths)`，判据是 `findOverlappingRoot(b, [a])?.relation === 'child'`。回到 `findOverlappingRoot`（`:34-45`），`relation === 'child'` 的含义是"**第一参数是第二参数的子目录**"（`:41` `if (c.startsWith(withSep(r))) return {root, relation:'child'}`，`c` 来自 candidate=b，`r` 来自 existing=a）。

- 迭代 `a='/a'`, `b='/a/b'`：`findOverlappingRoot('/a/b', ['/a'])` → `'/a/b'.startsWith('/a/')` 为真 → `{root:'/a', relation:'child'}` → **命中**，push `{root:'/a', nested:'/a/b'}` ✅
- 迭代 `a='/a/b'`, `b='/a'`：`findOverlappingRoot('/a', ['/a/b'])` → `'/a'.startsWith('/a/b/')` 假；`'/a/b'.startsWith('/a/')` 真 → 返回 `{root:'/a/b', relation:'parent'}` → `relation !== 'child'` → **不命中** ✅

即单向过滤确实让每对关系恰好产出一条，且 `root` 恒为外层。实测 P11 确认：`[{root:'/a', nested:'/a/b', relation:'child'}]`，长度 1。

**三层嵌套 3 对**：`findOverlappingRoot` 用的是纯 `startsWith` 前缀判断，不是"仅父层"，所以 `/a` 对 `/a/b/c` 也命中。3 个节点的有序对共 6 个（除自身），其中 3 个方向为 child、3 个为 parent → 恰好 3 对。测试 `settingsRepo.detectNested.test.ts:41-53` 断言的 `['/a/b⊃/a/b/c','/a⊃/a/b','/a⊃/a/b/c']` 与推演一致，且该用例在回归里是绿的。

**性能**：O(n²) × `findOverlappingRoot(b,[a])` 的单元素循环 = O(n²) 字符串前缀比较。守备目录个位数，实测无感。空表/单根不需要短路——`paths.length <= 1` 时内外层循环合计 0~1 次迭代且 `a===b` 直接 continue，天然是 O(1)。**不建议加短路**，那是无收益的复杂度。

**边界退化**：唯一能让它出错的输入是非规范形态（`'/media/tv/'` 的 `'//'` 拼接漏检）——实测 P7 确认 `['/media/tv/', '/media/tv']` 报 `[]`（这两者 `stripTrailingSep` 后相等，走 `:40` 的 `continue`，是**正确**行为，它们是别名不是嵌套）。至于"非规范根 + 其真子目录"的漏检，`findOverlappingRoot` 在 F3 已修（`:36-38` 双侧 `stripTrailingSep`），实测 `normalizeRoots.test.ts:70-78` 那条用例也覆盖了。`detectNestedRoots` 的"应在 normalizeRoots 之后"注释（`:301`）现在其实**不再是正确性必需**，只是保险。

## 迁移时机问题（`normalizeRoots` 该不该进 MIGRATIONS）

**核实**：`normalizeRoots()` 是运行时方法，`src/v2/db.ts:16` 的 `MIGRATIONS` 数组里没有它（grep 确认无引用）。spec 对 D7 的原文（`docs/design/2026-08-08-PIPELINE-SPEC.md:318`）是"已存在的嵌套配置在**迁移时**告警"——用了"迁移"这个词，但那句讲的是 detectNestedRoots 的告警，没有明文要求归一化进 `MIGRATIONS`。

**结论：当前处置可接受，理由充分**：
- 归一化的**下游消费者全在启动之后**（seedRootsFromEnv、detectNestedRoots、ingest 的 currentRoots），启动时跑一次就够
- 长期运行不重启的场景：脏数据的三个病（多扫一遍 / UI 删不掉 / D1 双算）都是**已经存在**的问题，不会因为晚修而恶化
- 进 `MIGRATIONS` 反而更危险：`db.ts:629-683` 的迁移链跑在 `openDb` 内、被 `db.transaction` 包裹，而 F7 的 UNIQUE 异常会让**整个 openDb 失败** → 数据库根本打不开，比现在的"cmdWatch crash"更难救

**但有一个真缺口**：`dashboard` 单独启动的路径（`src/dashboard/server.ts:209` `new SettingsRepo(db)`）**不跑** `normalizeRoots()`。若部署形态是 dashboard 与 watch 分进程（`src/cli/index.ts:592` 的 `startDashboard` 在 cmdWatch 内，看起来是同进程，所以当前不构成缺口），未来拆开时会漏。列为 F9 修法 2 的附带收益。

## 前瞻：第 1b 步的准备度

**1. `detectNestedRoots()` 的返回值形态**：不够，需要一层转换。D1 需要的是"**哪些 root 不安全**"（一个 `Set<string>`，用来在逐根差集时跳过），而当前返回的是"**哪些对是嵌套**"（`{root, nested, relation}[]`）。转换本身是一行 `new Set(pairs.flatMap(p => [p.root, p.nested]))`——注意**两端都要进不安全集**：外层根的差集会吃掉内层的行（C29 本体），内层根的差集虽然不会误删外层，但它与外层重复覆盖，差集语义已经不干净。建议 1b 直接在 `SettingsRepo` 上加 `unsafeRootsForDiff(): Set<string>`，别让 D1 的调用方自己 flatMap（那就是"写了列没人读"的孪生兄弟"读的人各写一遍口径不同"）。

**2. `removeRoot` 的 substr 前缀手法能否复用到 D1**：能，且**应该**复用——`substr(path,1,length(?)) = ?` 已经在 8+1 处一致使用，`%`/`_` 免疫这一点有测试锁着（`removeRootFiles.test.ts:73-84`）。**但必须先修 F8**：D1 的"库中该 root 下的行"查询要为**每个**守备目录跑一遍，若库里有 `'/'`，那一轮的 `prefix='/'` 会把全库行都算进"该 root 下"→ 差集比对的分母错成全库 → 任何一个挂载掉线都会引发全库删除。**F8 在 removeRoot 里是"一次点击毁库"，在 D1 里是"每日巡检自动毁库"**。这是 F8 必须在 1b 之前修的硬理由。

**3. 1a 遗漏的地基**：

## 对第 1b 步的前瞻建议（3 条）

1. **F8 必须先修，且要在 D1 的差集查询里再加一道防线**。`removeRoot` 的 `'/'` 缺陷在 D1 里会变成"每日巡检自动全库删除"——挂载掉线 + 库里有 `'/'` = C29 的最坏形态。别指望"用户不会填 `/`"，Docker 语境下这个填法完全符合直觉，且 `MEDIA_ROOTS=/` 实测能种进库（P5）。
